★★★ Mittel (20 Fragen)

51. Erkläre den Ablauf von der Lobby bis zur ersten Frage (inkl. COUNTDOWN).

1) Lobby: Spieler joinen, Controller binden, bereit setzen. 2) Host konfiguriert Spiel (POST /api/game/config). 3) Host startet (POST /api/game/start), wenn alle verbundenen Spieler ready. 4) Backend setzt state=COUNTDOWN, publiziert game/state. 5) 3s Countdown (game/countdown: 3,2,1). 6) state=QUESTION, Backend publiziert game/question mit Text und Optionen (ohne correctOption).

52. Wie wird erkannt, dass ein Controller offline ist?

Backend sendet Ping über controller/{id}/ping. Controller antwortet mit pong auf controller/{id}/pong. Bei 2 verpassten Pings (MISSED_PINGS_DISCONNECT) wird status=OFFLINE gesetzt. Ping-Intervall ca. 10s.

53. Wann endet eine Frage vorzeitig (ohne 30s abzuwarten)?

Wenn alle verbundenen Spieler geantwortet haben. GameStateManager nutzt countConnectedPlayersInSession und vergleicht mit der Anzahl der Antworten.

54. Wie funktioniert die Punkteberechnung (Zeitfaktor)?

Base-Punkte × Zeitfaktor. Zeitfaktor: <5s=1.0, 5–10s=0.9, 10–15s=0.8, 15–20s=0.7, 20–25s=0.6, 25–30s=0.5, >30s=0.0. Falsche Antwort = 0 Punkte.

55. Erkläre den Replay-Ablauf: Was passiert beim Zurück-zur-Lobby nach dem Spiel?

GameRepository.resetSessionToLobbyForReplay: 1) game_answers löschen, 2) game_session_questions löschen, 3) game_session_players.is_ready=0, 4) game_sessions.state=LOBBY. EventBus game.replay sendet ready=false an alle Spieler. Spieler bleiben in der Session, müssen erneut bereit klicken.

56. Welche MQTT-Topics subscribt der Web-Controller beim Start?

controller/{id}/ping, controller/{id}/status, game/state, game/question, game/evaluation, game/ended, game/countdown. Bei Binding zusätzlich: player/{id}/status, player/{id}/result.

57. Über welchen MQTT-Topic sendet der Controller seine Antwort?

player/{playerId}/answer – Payload: { questionId, selectedOption, playerId, controllerId }.

58. Warum wird die correctOption nicht im game/question-MQTT-Paket mitgeschickt?

Aus Sicherheitsgründen – der Client darf die richtige Antwort erst nach Ablauf der Antwortzeit (EVALUATION) erfahren, um Betrug zu verhindern.

59. Welche Rolle hat der GameStateManager?

Orchestriert den Spielablauf: reagiert auf EventBus (game.answer, game.cancel_countdown, game.replay), verwaltet Timer (Countdown, Frage 30s, Evaluation 3s), prüft ob alle verbundenen Spieler geantwortet haben, publiziert MQTT-Nachrichten und aktualisiert die DB.

60. Was passiert, wenn ein Spieler offline geht, während die Lobby läuft?

Nach 2 verpassten Pings: Controller status=OFFLINE. Spieler bleibt in game_session_players, erscheint im Frontend als "Offline". Spiel kann trotzdem gestartet werden, wenn alle verbundenen Spieler ready sind (areConnectedPlayersReady).

61. Welche Schicht ist zwischen AuthController und AuthRepository?

AuthService – Controller ruft Service auf, Service ruft Repository. Typische 3-Schichten-Architektur.

62. Wo werden die Fragen für eine Session zufällig ausgewählt?

GameRepository.fetchRandomQuestions – wählt basierend auf game_session_categories und allow_easy/medium/hard aus, ORDER BY RAND() LIMIT ?.

63. Was ist der Unterschied zwischen game_answers und game_session_results?

game_answers: einzelne Antworten pro Frage. game_session_results: aggregierte Ergebnisse pro Spieler (total_points, correct_count, answered_count) – wird aus game_answers berechnet (computeSessionResults).

64. Erkläre den Ablauf der RFID-Login-Idee (MQTT-basiert).

1) Arduino liest RFID-UID. 2) Arduino publiziert auth/rfid/lookup mit { uid, mac }. 3) Backend (MqttController) empfängt, ruft AuthService auf, sucht User by rfid_uid. 4) Backend publiziert auf controller/{mac}/rfid/reply mit { username }. 5) Arduino zeigt Benutzername an. (Hinweis: Arduino-Publish zu auth/rfid/lookup ist im Code evtl. noch nicht vollständig implementiert.)

65. Welche Docker-Container sind im Projekt definiert?

MariaDB, Mosquitto (MQTT), Java-Backend (Vert.x), nginx (Frontend/Reverse-Proxy), evtl. phpMyAdmin – siehe docker-compose.yml.

66. Wie unterscheidet sich das Frontend (Host-View) vom Web-Controller (Spieler-View)?

Frontend: Host-Ansicht, zeigt Lobby, Spielkonfiguration, Fragen, Auswertung, Highscores. Web-Controller: Spieler-Ansicht, nur A/B/C/D-Buttons, Ready-Toggle, Score. Läuft auf anderem Port (z.B. 81).

67. Wo wird verhindert, dass ein Spieler zweimal auf dieselbe Frage antwortet?

In GameRepository.saveAnswer – INSERT in game_answers. Bei Duplicate-Key (PRIMARY/UNIQUE) wird stattdessen ein Ergebnis mit duplicate=true zurückgegeben, Punkte werden nicht erneut gutgeschrieben.

68. Was passiert beim POST /api/controllers/disconnect genau?

ControllersService.disconnectController: 1) ControllersRepository.disconnectController setzt status=OFFLINE, assigned_user_id=NULL. 2) LobbyService entfernt Spieler aus Lobby (falls in Session). 3) EventBus publish lobby.updated.

69. Welche EventBus-Adressen nutzt der GameStateManager?

Consumer: game.answer, game.cancel_countdown, game.replay. Publisher: game.state, game.question, game.evaluation, game.ended, game.countdown – sowie Aufrufe an MqttService zum Publizieren auf MQTT.

70. Warum verwendet das Frontend MQTT statt HTTP-Polling für den Spielablauf?

Echtzeit – MQTT push-basiert: sofortige Updates (Fragen, Countdown, Auswertung) ohne Verzögerung. Polling wäre verzögert und belastender für Server und Netzwerk.

★★★★ Schwer (20 Fragen)

71. Zeige die SQL-Abfrage (oder beschreibe sie), mit der geprüft wird, ob alle verbundenen Spieler bereit sind.

SELECT COUNT(*) AS connected_total, SUM(CASE WHEN gsp.is_ready=1 THEN 1 ELSE 0 END) AS connected_ready FROM game_session_players gsp JOIN controllers c ON c.id=gsp.controller_id WHERE gsp.game_session_id=? AND c.status!='OFFLINE'. Ergebnis: ready wenn connected_total>0 und connected_ready==connected_total.

72. Wie wird sichergestellt, dass Offline-Spieler in der Auswertung mit 0 Punkten erscheinen?

computeSessionResults basiert auf game_session_players (alle Spieler in der Session), nicht nur auf game_answers. LEFT JOIN game_answers – Spieler ohne Antworten bekommen COALESCE(SUM(ga.points_awarded),0)=0.

73. Welche Zeile in welcher Datei setzt den controller status auf OFFLINE beim Disconnect?

ControllersRepository.disconnectController: UPDATE controllers SET status = 'OFFLINE', assigned_user_id = NULL WHERE controller_id = ?

74. Erkläre den Unterschied zwischen areAllPlayersReady und areConnectedPlayersReady.

areAllPlayersReady: alle Spieler in game_session_players müssen is_ready=1 haben. areConnectedPlayersReady: nur Spieler mit Controller status!='OFFLINE' müssen ready sein. Wichtig für Replay, wenn Offline-Spieler noch in der Session sind.

75. Wo wird die correct_option in game/question absichtlich ausgelassen (Code-Stelle)?

In GameStateManager oder MqttService – beim Bauen der MQTT-Payload für game/question wird das Feld correctOption weggelassen, damit der Client es nicht vor der Auswertung sieht.

76. Wie funktioniert das Controller-Binding per RFID (Schritt für Schritt)?

1) User hat rfid_uid in users. 2) Hardware-Controller (MAC) wird erkannt. 3) User hält RFID-Karte an Leser. 4) Arduino liest UID, publiziert auth/rfid/lookup. 5) Backend findet User, ermittelt passenden Controller. 6) POST /api/players/bind (oder MQTT) bindet Controller an User. Alternativ: manuelles Binding über Frontend ohne RFID.

77. Was passiert, wenn der Countdown läuft und ein Spieler auf "Nicht bereit" klickt?

EventBus game.cancel_countdown wird publiziert. GameStateManager bricht den Countdown ab, setzt state zurück auf LOBBY, publiziert game/state. Spiel startet nicht.

78. Welche Tabelle speichert die Verknüpfung Session–Kategorien?

game_session_categories – game_session_id, category_id. Ersetzt bei Config-Update (replaceSessionCategories: DELETE alt, INSERT neu).

79. In welcher Reihenfolge werden die Init-SQL-Skripte ausgeführt?

Alphabetisch: 00-init.sql (Schema), 01-seed-categories, 02–11 seed-questions, 12-seed-users, 13-seed-game-data, 14–16 weitere Seeds, 99-set-diana-not-ready. MariaDB-Container mountet das Verzeichnis und führt Skripte in Reihenfolge aus.

80. Warum wird navigator.sendBeacon für den Disconnect verwendet?

Zuverlässigkeit beim Seitenwechsel – sendBeacon garantiert, dass die Anfrage noch gesendet wird, selbst wenn die Seite gerade entladen wird. Normale fetch/XHR können dabei abgebrochen werden.

81. Welche Foreign Keys verweisen auf die Tabelle users?

controllers.assigned_user_id, game_sessions.host_user_id, game_session_players.user_id, game_answers.user_id, game_session_results.user_id, highscores.user_id.

82. Erkläre die Zeit-Buckets (T0_5, T5_10, …) in der Datenbank.

scoring_time_buckets: bucket_code, min_ms, max_ms, factor. T0_5: 0–5s, Faktor 1.0; T5_10: 0.9; … T30P: >30s, Faktor 0.0. Wird in GameRepository für Punkteberechnung verwendet (getTimeBucket, getTimeFactor).

83. Wo wird der Ping-Timer für Controller-Heartbeats gestartet?

Im MqttController bzw. MqttService – periodischer Vert.x-Timer, der controller/{id}/ping publiziert. Bei Empfang von pong wird last_seen_at aktualisiert. Bei Timeout (2 verpasste Pings) → status=OFFLINE, lobby.updated.

84. Wie unterscheiden sich game_session_questions und questions?

questions: Katalog aller Fragen (id, category_id, difficulty, question_text, correct_option, …). game_session_questions: Zuordnung welche Fragen in welcher Session gefragt werden (game_session_id, question_index, question_id, asked_at).

85. Was macht unbindControllerForUser in ControllersRepository?

UPDATE controllers SET status='FREE', assigned_user_id=NULL WHERE assigned_user_id=(SELECT id FROM users WHERE username=? LIMIT 1). Hebt die Spielerzuordnung auf – wird beim Lobby-Austritt (Austreten) aufgerufen.

86. Welche Bedingung muss erfüllt sein, damit POST /api/game/start erfolgreich ist?

1) Lobby-Session existiert (state=LOBBY). 2) areConnectedPlayersReady(sessionId) == true: Mindestens ein verbundener Spieler, alle verbundenen Spieler haben is_ready=1.

87. Wo wird der state der game_session auf COUNTDOWN gesetzt?

GameRepository.updateSessionState(sessionId, "COUNTDOWN", …) – aufgerufen von GameService.startGame nach erfolgreicher Ready-Prüfung.

88. Erkläre den Ablauf, wenn ein Spieler eine Frage beantwortet (von MQTT bis DB).

1) Controller publiziert player/{id}/answer. 2) MqttController empfängt, publiziert game.answer auf EventBus. 3) GameStateManager verarbeitet, ruft GameRepository.saveAnswer auf. 4) saveAnswer: Frage laden, Korrektheit prüfen, Punkte berechnen, INSERT in game_answers. 5) GameStateManager prüft ob alle verbunden geantwortet haben → evtl. frühes Ende der Frage.

89. Was passiert mit game_session_results beim Replay?

computeSessionResults wird bei ENDED aufgerufen und schreibt/aktualisiert game_session_results. Beim Replay: game_answers wird gelöscht, aber game_session_results bleibt zunächst. Beim nächsten computeSessionResults (nach neuem Spielende) werden die Werte überschrieben (ON DUPLICATE KEY UPDATE).

90. Welche Rolle hat MainVerticle beim Start der Anwendung?

Haupteinstiegspunkt: deployed HttpServerVerticle, MqttVerticle, GameStateManager. Registriert alle HTTP-Controller (Auth, Lobby, Game, Controllers, Player, Highscores, Object). Stellt Router und EventBus-Verbindungen bereit.

★★★★★ Sehr schwer (20 Fragen)

91. Skizziere die gesamte Architektur (Komponenten, Kommunikation) des Projekts.

Frontend (Browser) ↔ nginx ↔ Java Vert.x (HTTP). Vert.x ↔ MariaDB (JDBC). Vert.x ↔ Mosquitto (MQTT). Web-Controller ↔ MQTT + HTTP (disconnect). Arduino ↔ MQTT. EventBus verbindet: HttpController → Service → Repository; MqttController → EventBus; GameStateManager ↔ MQTT/DB. Kein direkter Frontend–DB; alles über Backend.

92. Welche Race Conditions könnten beim gleichzeitigen Ready-Setzen mehrerer Spieler auftreten?

Zwei Spieler klicken gleichzeitig Ready → beide UPDATEs auf game_session_players. Wenn Start-Check zwischen den Updates läuft, könnte ein Spieler fälschlich als nicht ready gelten. Durch sequentielle DB-Updates und Single-Threaded EventLoop von Vert.x wird das minimiert; dennoch sollte die Ready-Prüfung atomar sein (eine Abfrage).

93. Wie würde man eine neue Schwierigkeitsstufe (z.B. EXPERT) hinzufügen?

1) DB: ALTER TABLE questions MODIFY difficulty ENUM(...,'EXPERT'). 2) game_sessions: allow_expert Spalte. 3) GameRepository: BASE_POINTS, fetchRandomQuestions, updateSessionConfig. 4) Frontend: Checkbox/Konfiguration. 5) ALLOWED_MODES ggf. erweitern.

94. Warum könnte ein Spieler "Nicht bereit" anzeigen, obwohl er ready geklickt hat?

1) MQTT-Nachricht nicht angekommen. 2) Backend hat Lobby-Update nicht korrekt publiziert. 3) Frontend nutzt veraltete Daten (Cache). 4) Controller-Status OFFLINE → Frontend zeigt "Offline" statt Bereit. 5) game_session_players.is_ready wurde beim Replay auf 0 gesetzt.

95. Beschreibe einen vollständigen Testablauf: Registrierung bis zum Ende einer Runde.

1) POST /api/auth/register. 2) POST /api/auth/login. 3) POST /api/lobby/create. 4) POST /api/lobby/join (2–3 Spieler). 5) POST /api/controllers/create-web, POST /api/players/bind. 6) MQTT: player/{id}/ready. 7) POST /api/game/config. 8) POST /api/game/start. 9) MQTT: game/state COUNTDOWN→QUESTION. 10) MQTT: player/answer. 11) MQTT: game/evaluation, game/state. 12) Nach allen Fragen: game/ended, Highscores gespeichert.

96. Wie würde man das Projekt um einen "Pause"-Zustand erweitern?

1) game_sessions.state: PAUSED hinzufügen. 2) Neuer Endpoint oder MQTT: game/pause. 3) GameStateManager: Bei PAUSED Timer stoppen, state speichern. 4) game/resume: Timer fortsetzen. 5) Frontend: Pause-Button für Host, Anzeige "Pausiert" für alle.

97. Welche Fehlerbehandlung fehlt oder wäre zu verbessern?

Beispiele: Keine Retry-Logik bei MQTT-Disconnect. Keine Validierung von questionId/selectedOption vor saveAnswer. Keine Transaktion bei resetSessionToLobbyForReplay (mehrere DELETEs/UPDATEs). Kein Timeout bei langsamen DB-Abfragen. Fehlende Logs für Debugging. 409/400 oft generisch.

98. Erkläre die Abhängigkeiten zwischen LobbyService und ControllersRepository.

LobbyService braucht ControllersRepository für unbindControllerForUser beim removePlayerFromLobby (Austreten). LobbyService ruft zuerst unbind auf (best-effort), dann lobbyRepository.removePlayerFromLobby. Bei Fehler von unbind wird trotzdem removePlayerFromLobby ausgeführt (Spieler soll Lobby verlassen können).

99. Was passiert, wenn zwei Lobbys gleichzeitig existieren (edge case)?

getLobbySessionId holt "ORDER BY id DESC LIMIT 1" – also die neueste LOBBY-Session. Alte Lobbys können im State LOBBY bleiben. Spieler könnten versehentlich zur falschen Lobby joinen. Typischerweise wird nur eine Lobby aktiv gehalten; ggf. sollte vor create geprüft werden, ob bereits eine existiert.

100. Wie funktioniert die Reihenfolge der Fragen (question_index)?

game_session_questions hat question_index (1, 2, 3, …). fetchRandomQuestions wählt zufällige Fragen, insertSessionQuestions speichert sie mit aufsteigendem question_index. GameStateManager lädt die aktuelle Frage anhand des Index und wechselt nach Evaluation zum nächsten.

101. Warum wird Vert.x statt Spring Boot verwendet?

Vermutlich Projektvorgabe oder Leichtgewichtigkeit. Vert.x: reaktiv, EventLoop-basiert, geringer Footprint, integrierte MQTT-Unterstützung, EventBus für interne Kommunikation. Gut geeignet für IoT/ Echtzeit-Anwendungen mit vielen gleichzeitigen Verbindungen.

102. Wie würde man das System um mehrere parallele Spielrunden erweitern?

1) Lobby-Code: Session-ID statt "die eine" Lobby. 2) game_session_id in allen MQTT-Topics oder als Prefix. 3) GameStateManager pro Session (Map sessionId→State). 4) Frontend: Lobby-Auswahl, Join mit sessionId. 5) Einschränkung: Ein Controller kann nur in einer Session sein.

103. Wo und wie wird die Session-ID an die MQTT-Clients kommuniziert?

Topics sind global (game/state, game/question) – es gibt nur eine aktive Session. sessionId wird ggf. in Payload von game/ended mitgeschickt. Für Multi-Session müsste sessionId im Topic sein (z.B. game/{sessionId}/state). Aktuell: implizit "die aktive Lobby-Session".

104. Welche Sicherheitslücken könnten bestehen?

1) MQTT ohne Auth: jeder kann subscriben/publishen. 2) Keine Session/Token-Validierung bei manchen Endpoints. 3) RFID-UID könnte gespooft werden. 4) correctOption im Frontend nach Evaluation – OK. 5) SQL Injection: Prepared Statements werden genutzt – gut. 6) CORS/Origin-Checks je nach Deployment.

105. Erkläre den Ablauf von game.replay auf dem EventBus.

GameController (oder GameStateManager) publiziert game.replay mit sessionId. GameStateManager (oder MqttService) consumer: ruft resetSessionToLobbyForReplay auf, sendet MQTT ready=false an alle Spieler (player/{id}/status), damit Controller/Frontend den Ready-Status zurücksetzen.

106. Was passiert, wenn während einer Frage der MQTT-Broker ausfällt?

Neue Zustandsänderungen (Evaluation, nächste Frage) kommen nicht beim Frontend/Controller an. Antworten könnten über MQTT verloren gehen – Backend empfängt sie nicht. DB- und EventBus-Logik laufen weiter. Nach Reconnect: Clients müssen ggf. state neu abfragen (GET /api/lobby/status, game state) – Reconnect-Logik müsste implementiert sein.

107. Wie ist die Beziehung zwischen controllers.id und controllers.controller_id?

id: Primary Key, Auto-Increment, intern. controller_id: Eindeutiger String (z.B. UUID für Web-Controller, MAC für Hardware), wird in MQTT-Topics und API verwendet. game_session_players.controller_id ist FK zu controllers.id (nicht controller_id) – Verweis auf die Zeile.

108. Welche Änderungen waren nötig, um Offline-Spieler korrekt zu unterstützen?

1) areConnectedPlayersReady statt areAllPlayersReady für Spielstart. 2) countConnectedPlayersInSession für vorzeitiges Fragen-Ende. 3) computeSessionResults basierend auf game_session_players (alle Spieler, auch ohne Antworten). 4) Frontend: "Offline" statt "Bereit/Nicht bereit" anzeigen. 5) canStartGame im Frontend nur verbundene Spieler prüfen.

109. Wie würde man das Projekt um einen "Spectator"-Modus erweitern?

1) Neuer User-Typ oder Flag is_spectator. 2) Spectator joinet Lobby, aber wird nicht in game_session_players eingetragen. 3) Subscribt nur game/state, game/question, game/evaluation, game/ended – keine player-Topics. 4) Frontend: Read-Only-Ansicht ohne Antwort-Buttons. 5) Keine Punkte, keine Ready-Pflicht.

110. Fasse die wichtigsten Unterschiede zwischen main und main-test zusammen (aus dem Git-Diff).

main-test enthält: Arduino (RFID, OLED, Buttons, NeoPixel, WiFi/MQTT), erweiterte Frontend- und Web-Controller-Logik, Lobby (create/join/leave mit Controller-Unbind), Game (config, start, areConnectedPlayersReady), Controllers (create-web, disconnect), Player-Binding, RFID-Auth, MQTT-Integration, Offline-Spieler-Support, Replay-Logik. main ist die Basis ohne diese Erweiterungen.
